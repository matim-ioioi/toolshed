# Вклад в проект

## Формат сообщений коммитов

Проект следует [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/). Сообщение коммита имеет вид:

```
<тип>(<область>): <описание>
```

Область необязательна. Допустимые типы: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`. Breaking change помечается `!` после типа/области (`feat!: …`) либо футером `BREAKING CHANGE: …`.

Формат проверяется на двух уровнях, и оба используют один и тот же commitlint (`commitlint.config.mjs`, набор правил `@commitlint/config-conventional`):

- **Локально** — git-хук `commit-msg` (husky). Некорректное сообщение отклоняется до создания коммита. Чтобы хук заработал, после клона выполните `pnpm install` — скрипт `prepare` установит husky.
- **На CI** — workflow `Commitlint` на событие `pull_request` прогоняет commitlint по всем коммитам диапазона pull request'а.

## Релиз и версионирование

Версионирование пакета полностью автоматическое и выполняется semantic-release согласно `.releaserc.json`. После мёржа в `main` запускается workflow `Release`: semantic-release анализирует историю коммитов начиная с предыдущего тега релиза и вычисляет следующую версию по стандартным правилам Semantic Versioning на основе типов коммитов Conventional Commits — breaking change повышает major, `feat` повышает minor, а каждый другой распознаваемый тип, кроме `chore`, повышает patch. Диапазон коммитов берётся целиком с момента предыдущего релиза, поэтому один смёрженный pull request — независимо от того, сколько коммитов он принёс, — даёт ровно одно повышение версии.

Тип `chore` — единственное намеренное исключение: он не повышает версию. Причина в том, что собственный коммит автоматизации имеет тип `chore(release): …`; если бы `chore` давал повышение, такой коммит мог бы запустить лишний релиз. Поэтому pull request, состоящий только из `chore`-коммитов, релиза не создаёт — но эти коммиты не теряются: они войдут в следующий релиз вместе с коммитом, который его вызовет.

Если среди коммитов с момента предыдущего релиза нет ни одного, дающего повышение версии, релиз не создаётся вовсе — это нормальное поведение, а не сбой.

Когда повышение версии есть, semantic-release последовательно обновляет `CHANGELOG.md`, повышает версию в `package.json`, коммитит оба файла как `chore(release): X.Y.Z [skip ci]`, создаёт тег `vX.Y.Z`, пушит коммит и тег в дефолтную ветку и создаёт GitHub Release. Повторный запуск на этом же релизном коммите предотвращён сразу тремя механизмами: (1) токеном `[skip ci]` в сообщении коммита — GitHub Actions пропускает запуск workflow, если он есть в сообщении коммита; (2) условием `if` в workflow `Release`, исключающим коммиты, чей заголовок начинается с `chore(release): `; (3) самим фактом, что пуш выполнен встроенным `GITHUB_TOKEN` — события, инициированные этим токеном, по правилам GitHub Actions не порождают новых запусков workflow.

### Соответствие типов коммитов разделам changelog

Каждый коммит, оформленный по правилам Conventional Commits, попадает в соответствующий раздел `CHANGELOG.md`. Восемь разделов всегда видимы:

- `### ⚠ BREAKING CHANGES` — коммиты с пометкой о breaking change;
- `### Features` — `feat`;
- `### Bug Fixes` — `fix`;
- `### Performance Improvements` — `perf`;
- `### Code Refactoring` — `refactor`;
- `### Reverts` — `revert`;
- `### Documentation` — `docs`;
- `### Other Changes` — любой распознаваемый, но не перечисленный явно тип коммита; такие коммиты не пропадают, а попадают именно сюда.

Ещё пять типов коммитов тоже порождают записи, но сворачиваются в единый блок `Maintenance`, который по умолчанию скрыт и раскрывается по клику:

- `### Styles` — `style`;
- `### Tests` — `test`;
- `### Build System` — `build`;
- `### Continuous Integration` — `ci`;
- `### Chores` — `chore`.

Коммиты, заголовок которых не удаётся разобрать как Conventional Commit, не порождают запись в changelog вовсе — джоб релиза лишь логирует такой коммит как предупреждение. Merge-коммиты и собственные коммиты автоматизации вида `chore(release): …` тоже никогда не попадают в changelog.

### Обязательная настройка GitHub

Механизм релиза зависит от настроек, которые находятся вне репозитория и не могут быть проверены никаким кодом отсюда.

**Settings → General → Pull Requests → «Allow squash merging»** должна быть выключена (оставьте merge commit и/или rebase).

Причина: squash-merge схлопывает весь pull request в один коммит в целевой ветке, чьё сообщение по умолчанию берётся из заголовка pull request. В результате исходные коммиты `feat(...)`, `fix(...)` и другие никогда не попадают в дефолтную ветку, и ни один генератор не может их восстановить постфактум. Если история уже была смёржена со squash — восстановить её невозможно. Merge-коммит, напротив, безопасен: semantic-release его игнорирует, а принесённые pull request'ом коммиты видит целиком.

**Settings → Actions → General → Workflow permissions** — Actions должны иметь право записи. Здесь каждый workflow объявляет нужные права сам через блок `permissions` (`Release` запрашивает `contents: write`, `issues: write`, `pull-requests: write`), но если на уровне организации/репозитория стоит «read-only» без разрешения повышать права из workflow — выставьте «Read and write permissions», иначе релизный пуш и создание GitHub Release упадут с ошибкой доступа.

**Settings → Branches (или Rules) → защита ветки `main`** — рекомендуется, но с оговоркой. Если вы включаете защиту с «Require a pull request before merging» или ограничением на прямой пуш, встроенный `GITHUB_TOKEN` не сможет запушить релизный коммит и тег, и джоб `Release` упадёт с ошибкой доступа. В этом случае:

- добавьте обход (bypass) для учётной записи/GitHub App, от имени которой идёт релиз, в правилах защиты ветки; **или**
- используйте отдельный токен с правом пуша (Personal Access Token или токен GitHub App), положите его в секрет репозитория и подставьте в `env` джоба `Release` вместо `GITHUB_TOKEN`.

Ослаблять защиту ветки `main` целиком ради «починки» падающего пуша нельзя — обход должен быть точечным, только для релизной учётной записи.

### Токен CI

Базовый сценарий не требует ручных секретов. GitHub Actions автоматически выдаёт каждому запуску встроенный `GITHUB_TOKEN`, а semantic-release и `@semantic-release/github` читают его из окружения (в джобе `Release` он проброшен как `env: GITHUB_TOKEN`). Прав, объявленных в workflow (`contents: write`, `issues: write`, `pull-requests: write`), достаточно для пуша тега и релизного коммита в дефолтную ветку и для создания GitHub Release через API.

Отдельный токен (Personal Access Token или GitHub App) нужен только в двух случаях:

- ветка `main` защищена так, что встроенный токен не может в неё пушить (см. настройку выше);
- нужно, чтобы релизный пуш или созданный тег сами запускали другие workflow. События, инициированные встроенным `GITHUB_TOKEN`, не порождают новых запусков — здесь это, наоборот, полезно и служит одним из механизмов разрыва цикла самозапуска релиза.

### Безопасность CI

Workflow `Commitlint` запускается на событие `pull_request` и выполняет установку зависимостей из ветки контрибьютора. Он умышленно:

- объявляет `permissions: contents: read` — только чтение;
- ставит зависимости с флагом `--ignore-scripts`, поэтому lifecycle-скрипты пакетов из дерева зависимостей не выполняются;
- полагается на модель GitHub: для pull request из форков встроенный токен доступен только на чтение, а секреты репозитория в такой запуск не передаются.

Джоб `Release` выполняется только на пуше в `main` (то есть на уже принятом коде) и тоже ставит зависимости с `--ignore-scripts`.

### Node в CI

Оба workflow работают в контейнере `node:22.23.1-alpine`. Версия node зафиксирована конкретным патчем, а не плавающим тегом `22-alpine`: некоторые сборки corepack уходили в npm-registry за «latest stable» pnpm ещё до чтения `packageManager` в `package.json` и падали на проверке подписи. Зафиксированный образ несёт исправленный corepack.

pnpm поднимается через `corepack enable` — не через `corepack prepare … --activate`: активация кеширует версию без учёта sha512, и тогда любой следующий `pnpm@9.15.4+sha512.*` (в том числе подделанный) отдавался бы из кеша без проверки целостности. Версию pnpm и её sha512 берём только из поля `packageManager` в `package.json` — так проверка целостности реально работает.

### Зависимости

Все npm-зависимости закреплены на точных версиях без диапазонов `^` / `~` — это обеспечивается `save-exact=true` в `.npmrc`. При добавлении зависимости фиксируйте её точную версию.
